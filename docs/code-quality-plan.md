# Code quality plan

The code in this repo is written by AI, and there's too much of it for a human to review line by line. The PR checks are the gatekeeper: a change merges only when every required check passes. This doc lists the checkers we plan to add, what each one is worth, and which are done.

**How to use this doc:** implement items in any order within a phase, preferably one PR per item. Tick the box in the same PR that adds the checker, and note anything worth remembering (thresholds chosen, rules disabled and why) under the item. Follow-up work too big to do along the way, such as fixing a checker's baseline, goes in a GitHub issue with the `code-quality` label, with enough detail to pick it up in a later session.

## Decisions

- **All changes go through PRs.** Work happens on a branch and merges into `main` only after the required checks pass. The admin bypass for pushing directly to `main` stays, but only for emergencies.
- **Baseline existing findings and gate only new code.** Detekt, Android Lint and the duplication checker would report hundreds of findings on the existing code. Each records them in a baseline file so new code is checked strictly, and the baselines are reduced over time. Baselines should only shrink; a PR that grows one needs a good reason.
- **One local command.** All static checks run from a single task, `./gradlew qualityGate`, listed in CLAUDE.md, so the agent can run the same checks before committing instead of waiting for CI to fail.

## Phase 1: make the gate real

- [x] **Branch ruleset on `main`.** Require PRs and require the PR checks to pass before merging; keep the admin bypass for emergencies.
  *Value:* without this, every other checker only reports and doesn't block anything.
  *Notes:* the "default branch" ruleset requires a PR, the Unit Tests, Debug Build, Release Build, Gitleaks, Dependency Review and Quality Gate checks, an up-to-date branch and squash merges, with an admin bypass. Add each new checker's job to the required checks once it has run on a PR. It also requires 1 approval, which GitHub doesn't let you give on your own PR, so for now every merge goes through the admin bypass after you've checked the PR. That stays until all phases are done and the checks have earned enough trust to set approvals to 0.
- [x] **Clean up the workflows.**
  - Add `permissions: contents: read` to `pr-checks.yml` (it has none, so it gets the default token permissions).
  - Remove the `develop` branch target from `pr-checks.yml`; that branch doesn't exist.
  - Delete `unit-tests.yml`; `debug-release.yml` already runs the same tests on every push to `main`.
  - Combine the PR jobs where it saves setup time, ending in one quality gate task.

  *Value:* less CI time, and a smaller token scope if a workflow step is compromised.
  *Notes:* the PR jobs stay separate: they run in parallel, so the PR finishes sooner, and Actions minutes are free for public repos. Combining them into one gate task happens in Phase 2. The repo's default workflow token is already read-only.
- [x] **Dependabot** for Gradle (the version catalog) and GitHub Actions, with related updates grouped (e.g. all AndroidX, all Ktor) to keep the PR count manageable.
  *Value:* dependencies stay current without manual work, and the required checks validate each update PR automatically.
  *Notes:* configured in `.github/dependabot.yml`, with a 7-day cooldown on new releases (security updates skip it). Dependabot alerts and security updates are on in the repo settings. Check whether the Gradle wrapper gets updates; if not, update it by hand. The devcontainer it also updated was removed, since JetBrains' devcontainer support doesn't work well with Android Studio. `gradle/actions` is on v6 with `cache-provider: basic` on every step: v6's default cache is a proprietary Gradle component covered by Gradle's Terms of Use, and the basic one is open source and caches the same way.
- [x] **Dependency review action** on PRs, failing on known-vulnerable dependencies and on licenses that conflict with ours.
  *Value:* Dependabot fixes what's already in the repo; this stops new problems from coming in through a PR.
  *Notes:* GitHub can't read Gradle dependencies itself, so `dependency-review.yml` builds the dependency graph with Gradle and submits it on every PR and push to main. Only GitHub's own code sees the write token. Allowed licenses are the ones compatible with GPL-3.0. It blocks on vulnerabilities in build tooling and tests too, not only in libraries that ship in the app, since the tooling runs in CI next to the signing key. Licenses are only checked for what goes into the debug and release APKs, since build tooling and tests aren't distributed with the app; the graph labels those libraries "runtime" and everything else "development". A library whose license GitHub can't detect passes without a license check (today that's some AndroidX and JetBrains lifecycle libraries, which are Apache-2.0), so check a new library's license by hand when the review lists it as undetected. Its first runs had no graph for `main` to compare with, so they checked every dependency. They found vulnerable versions of Bouncy Castle (1 critical), jose4j, jdom2, commons-lang3 and httpclient, all brought in by AGP, in the build classpath and in each module's lint tooling (`androidLintTool`). The review only reported some of them, so the rest were found by checking every resolved dependency against GitHub's advisory database.
  *Fixing a flagged build tooling library:* add its fixed version to the `security-fixes` bundle in `gradle/libs.versions.toml`, and add it to the matching Dependabot group. `build.gradle.kts` requires every library in the bundle as a constraint, which only raises a version and never adds a library. Remove an entry once AGP brings in a fixed version itself.
- [x] **GitHub secret scanning with push protection** (repo setting; free for public repos).
  *Value:* Gitleaks reports a secret after it's been pushed. Push protection rejects the push.
  *Notes:* both are on. Scanning for generic (non-provider) patterns and checking whether found secrets are still valid are left off.

## Phase 2: static analysis on every PR

- [x] **Detekt** with the Compose rules plugin, plus a baseline.
  *Value:* hard limits on function length, complexity and nesting; catches magic numbers, swallowed exceptions, unused private code and Compose mistakes (modifier order, unstable parameters, state hoisting). Models tend to write long functions that work but are hard to maintain.
  *Notes:* Detekt 2.0.0-alpha.6 with the Compose rules 0.6.8, configured in `config/detekt/detekt.yml` on top of Detekt's defaults. It's an alpha because Detekt 1.23, the last stable release, is built for Kotlin 2.0 and the Compose rules need 2.0. `qualityGate` runs the type-resolution tasks, which enable the rules that need types: `:shared:detektMainAndroid`, `:shared:detektHostTestAndroid` and `:androidApp:detektDebug` (debug and release have the same code). This is the main static analysis for `shared`, since Android Lint can't check it. The config only adjusts rules that clash with Compose or ktlint: 140-character lines, and `@Composable` functions may be PascalCase, use literal sizes and take many parameters. Two rules were changed while fixing #20: `ReturnCount` doesn't count guard clauses (early `?: return`), and `TooManyFunctions` is off. A function count says little about cohesion (a view model has a function per user action, the API client one per endpoint), it punished splitting long functions into helpers, and the classes that were genuinely too big were all caught by `LargeClass` too. `LargeClass` stays as the only check that notices a class growing; when it flags a class that is big but cohesive, suppress it with the reason. While fixing #23, `MagicNumber` was set to ignore the arguments of enum entries, since an entry's name (`FIFTEEN_MINUTES("15 minutes", 15L)`) already says what its numbers mean. The 365 existing findings are in the baselines (`shared/detekt-baseline-main.xml`, `shared/detekt-baseline-hostTest.xml`, `androidApp/detekt-baseline-debug.xml`); the biggest groups are generic `catch (e: Exception)` (which also catches coroutine cancellation), long or complex functions, magic numbers and unsafe `!!`. Fix findings in code you touch and remove them from the baseline, so it only shrinks. Baseline entries match by rule and signature, not line, so one entry can cover several findings in a file (every `catch (e: Exception)` in it, for example), and a new finding of the same kind in that file isn't flagged until the entry is removed. Fixing the baseline is tracked in GitHub issues #18 to #23 (label `code-quality`), one per theme, each listing its findings.
  *Known bug:* `:shared:detektMainAndroid` prints "There were 6 compiler errors found during analysis. This affects accuracy of reporting." and still passes. Detekt 2.0.0-alpha.6 analyzes `commonMain` and `androidMain` as one module, so each `expect`/`actual` pair (`createHttpClient()` and `platformModule()`) gets "expect and corresponding actual are declared in the same module" errors, three per pair. Compiler arguments can't fix it: Detekt adds the source files without the fragment options that describe which source set refines which. It's [detekt/detekt#9602](https://github.com/detekt/detekt/issues/9602), still open; the `-Xmulti-platform` fix for [#7533](https://github.com/detekt/detekt/issues/7533) doesn't cover it. On 2026-10-18 it changed nothing: running without the baseline gave the same 115 findings as a run with the `expect`/`actual` keywords removed (no errors). The risk is that the errors are silent, so a new `expect`/`actual` pair or a classpath problem could add more without anyone noticing, and the upstream report found false `UnusedPrivateProperty` findings caused by it. Check for the fix when upgrading Detekt. To see the messages, set `debug = true` in the `detekt` block of `build.gradle.kts` and run the task with `--rerun` (`debug` isn't a task input, so a cached run prints nothing). Background on the declarations: [Kotlin's expect/actual docs](https://kotlinlang.org/docs/multiplatform/multiplatform-expect-actual.html).
- [x] **ktlint** (through Spotless or the ktlint Gradle plugin), with auto-fix available locally.
  *Value:* one deterministic style for every model, so diffs show real changes instead of formatting churn.
  *Notes:* Spotless runs ktlint with the official Kotlin style, configured in `.editorconfig` (140-character lines, PascalCase allowed for `@Composable` functions); `qualityGate` runs `spotlessCheck`, and `./gradlew spotlessApply` fixes what it can. The one-time reformat (#14) is listed in `.git-blame-ignore-revs`, so blame skips it; run `git config blame.ignoreRevsFile .git-blame-ignore-revs` once for local `git blame` to do the same. Spotless doesn't write any formatting to a file that still has an error ktlint can't fix, so #14 skipped 13 files; they were fixed by hand and formatted in the next PR. ktlint moved one end-of-line comment onto the wrong code during the reformat, so check comments after a ktlint upgrade reformats code. ktlint doesn't flag long comments.
- [x] **Duplication detection** (PMD CPD with Kotlin support, or jscpd), failing if duplication increases compared with `main`.
  *Value:* models often copy a similar function instead of extracting it or reusing one. This is the main problem we want to stop. Lower the threshold over time.
  *Notes:* PMD's copy-paste detector (CPD) 7.28.0, run from PMD's own CLI artifact, finds Kotlin blocks of at least 50 tokens duplicated in the production code (`shared`'s `commonMain` and `androidMain`, and the app). `qualityGate` runs `cpdCheck`, which compares the findings with `config/cpd/cpd-baseline.txt` and fails on any duplicate not in it. A duplicate is identified by its files and a hash of its code, so removing one doesn't make room for another, and editing a duplicated block makes it new, which forces deduplicating code that's touched. `./gradlew cpdBaseline` rewrites the baseline; only use it to drop fixed entries. The 19 duplicates (430 lines) that existed when it was added, at a 100-token minimum, were all removed in #24. The minimum was then lowered to 50 (`-Pcpd.minimumTokens=N` overrides it): comparing 100 to 40, nearly every finding down to 50 was real copied code, while at 40 about half of the 47 findings were noise such as pass-through function signatures and the parameter lists of sibling composables. The 20 duplicates found at 50 were removed in #40, so the baseline is empty. Code that should stay separate even though it looks alike, like the light and dark palettes in `Theme.kt`, is wrapped in `// CPD-OFF` / `// CPD-ON` with the reason. Tests aren't checked.
- [x] **Android Lint** with `warningsAsErrors`, a baseline, and `checkDependencies` so it also covers `shared`.
  *Value:* catches API calls above `minSdk 24`, manifest security issues, accessibility problems (missing content descriptions, small touch targets) and unused resources: Android-specific bugs the other tools don't know about.
  *Notes:* runs as `:androidApp:lintDebug` through `qualityGate`, which CI runs as the Quality Gate check. It only covers `androidApp`: the KMP library plugin `shared` uses has no lint for its main code, and `checkDependencies` doesn't reach it either (tested with a deliberate issue). `shared` is mostly plain Kotlin, so Detekt covers it instead. Of the 21 starting issues, 16 were fixed or suppressed with a reason (JavaScript in the two WebViews, the launcher icon's long vector paths), and the other 3 were fixed afterwards, so there's no baseline: the launcher icon got a monochrome layer for themed icons, generated from the icon's own shapes, and the reply bar now uses the window height instead of `Configuration.screenHeightDp`. The checks that fail when something new is released are off, so results don't change from one day to the next: `NewerVersionAvailable`, `GradleDependency`, `AndroidGradlePluginVersion` and `OldTargetApi`. Dependabot covers the dependencies, but nothing covers `targetSdk`, so update it by hand after each Android release. It's 37, the same as `compileSdk`; going from 36 needed no code changes, since none of Android 17's changes for apps targeting it touch anything the app uses. Testing found one platform bug: on the first Android 17 release (emulator build CE2A.260420.019), apps targeting 37 get the new lock-free `MessageQueue`, and video decoding fails because SELinux denies the decoder a `MessageQueue` memfd. Android 17 QPR2 (CP41.260831.007) and a Pixel 11 Pro on CD1A.261005.003 play video fine, so it was fixed before 37 was merged. If videos ever show black on an Android 17 phone, check its build first.
- [x] **Kotlin compiler `allWarningsAsErrors`** in both modules.
  *Value:* nearly free. Stops deprecated APIs, unused variables and unchecked casts from piling up as warnings nobody reads.
  *Notes:* on for every compilation in `shared` and `androidApp`, tests included. The only warning was an unnecessary `!!`. Kotlin 2's compiler doesn't report unused variables (the IDE does), so Detekt has to catch those. Warnings Gradle reports about the build scripts themselves aren't covered; the only one, a deprecated `androidLibrary` block, was renamed to `android`.

## Phase 3: security and architecture

- [x] **CodeQL** (java-kotlin, `security-extended` queries) on PRs and on a weekly schedule.
  *Value:* data-flow analysis that follows untrusted input (intents, deep links, network responses) to dangerous sinks: injection, unsafe WebView settings, logged secrets, weak crypto. Matters because the app handles Reddit OAuth tokens.
  *Notes:* `codeql.yml` runs on PRs, on pushes to `main` (so PRs have results to compare with) and every Monday. It's an advanced setup rather than GitHub's default setup, because the default setup analyzes java-kotlin without building, which only covers Java and skips all our Kotlin. Leave the default setup off in the repo settings; the two can't run together. It also analyzes the `actions` language, the workflow files, since that costs nothing extra. CodeQL reads Kotlin by watching the compiler, so the build step builds `:androidApp:assembleDebug` without the build cache or a Gradle daemon and with the Kotlin compiler in Gradle's process; a cached build gives it no code to analyze. Three Android rules are turned off in `.github/codeql/codeql-config.yml` and replaced by tests in `konsistTest`, because they can't read this app's Kotlin. GitHub matches an alert across scans by a fingerprint of the code around it, so a dismissed alert comes back as a new one whenever nearby code changes (#11 and #12 came back as #21 and #22 after #60 added three lines nearby), and blocks the PR that touches it. `websettings-allow-content-access` flags every read of Compose state that holds a WebView and can't follow the WebView through `apply` blocks (#51); `webViewsTurnOffContentAndFileAccess` checks that every file creating a WebView turns off content and file access once per WebView. `websettings-javascript-enabled` flags JavaScript, which the pages need (#52); `noJavaScriptInterfaces` checks for what would make it unsafe, a JavaScript interface. `backup-enabled` only sees `android:allowBackup="true"` (#53); `BackupRulesTest` checks that both backup rule files exclude the token file (its name read from `PlatformModule.android.kt`) and `app_webview/`, that they match, and that the manifest uses them. Turn a rule off only with a test that checks what it was meant to catch. CodeQL 2.27 supports Kotlin up to 2.4.20, so check its [supported versions](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/) before a Kotlin minor upgrade: a Kotlin release it doesn't support yet fails the job. To check what it extracted, rerun the `java-kotlin` job with debug logging (`gh run rerun <run> --job <job> --debug`): it uploads the database and the extractor logs as an artifact, and `src.zip` in the database lists every file analyzed. The first run extracted all 113 production `.kt` files with Kotlin 2.4.21. Its extractor logs had about 300 warnings, all `Couldn't find a Java equivalent function` or `Missing type argument`, which are normal for Kotlin and don't drop any files. The `actions` analysis flags third-party actions (not `actions/*` or `github/*`) that aren't pinned to a commit SHA (`actions/unpinned-tag`); the zizmor item below fixes those.
- [x] **zizmor and actionlint** for the workflow files, and pin every action to a commit SHA (Dependabot keeps the SHAs current).
  *Value:* the workflows handle the signing key and a `contents: write` token, which makes them the most attractive target in the repo. These tools catch template injection, overly broad permissions and unpinned actions.
  Also fail when a `gradle/actions` step doesn't set `cache-provider: basic`, so the proprietary cache can't come back unnoticed.
  *Notes:* `qualityGate` runs three new tasks: `actionlint` (1.7.12, with shellcheck 0.11.0 for the `run:` scripts), `zizmor` (1.30.1) and `gradleActionsCacheCheck`. Gradle downloads the tools from their GitHub releases for Linux and macOS on x86_64 and arm64, and refuses an archive whose SHA-256 doesn't match the one pinned in `build.gradle.kts`, so nothing has to be installed and every machine runs the same versions. shellcheck is downloaded too, because actionlint only uses it when it's installed, which would make local and CI results differ. Dependabot can't update these tools, so update them by hand; the comment above `releaseTools` says how. zizmor runs with `--strict-collection`, because without it a workflow it can't parse is skipped with only a warning. With a token in `GH_TOKEN` it also runs its online audits, which check that each pinned SHA is a commit in the action's own repo (not a fork's) and that no action has a known vulnerability. The Quality Gate job sets the token, so those audits only run in CI unless you set it locally (`GH_TOKEN=$(gh auth token) ./gradlew zizmor`). Every action is pinned to the commit of a release, with the version in a comment (`@<sha> # v7.0.1`), which Dependabot updates along with the SHA. Fixing the first findings: every checkout sets `persist-credentials: false`, so the token isn't left in `.git/config` for later steps; the tag-triggered release build sets `cache-disabled: true`, so a poisoned cache entry can't get into a published APK; and the debug release finds `apksigner` with `find` instead of `ls` (shellcheck SC2012). The same SHA pins also clear CodeQL's `actions/unpinned-tag` alerts.
- [x] **Architecture tests with Konsist.** Start with:
  - No hardcoded colors outside `Theme.kt` (the existing CLAUDE.md rule)
  - No `android.*` imports in `shared/commonMain`
  - UI code doesn't call the API client directly

  *Value:* turns the written rules in CLAUDE.md into failing tests. Models forget or ignore written rules; they can't ignore a failing test. Add a test whenever a new rule goes into CLAUDE.md.
  *Notes:* Konsist 0.18.1 in a new `konsistTest` module, whose tests `qualityGate` runs (`:konsistTest:test`, plus Detekt on them). `ArchitectureTest` checks the production source sets (`androidApp/src/main`, `shared/src/commonMain`, `shared/src/androidMain`) for five rules:
  - **No hardcoded colors outside `Theme.kt`:** a `Color(...)` whose first argument is a number, or a named color like `Color.Black` or `Color.parseColor`. `Color(argb)` with a computed value (flair colors from Reddit) and `Color.Transparent`/`Color.Unspecified` are allowed. Tests aren't checked, since CLAUDE.md only asks them to use the constants where they can.
  - **`commonMain` only imports multiplatform code:** imports must come from an allowed list in `Rules.commonMainImportPrefixes` (Kotlin, kotlinx, Ktor, Koin, multiplatform-settings, Napier, AndroidX Lifecycle and the shared code). A new multiplatform library has to be added there, after checking it supports more than Android. This is stricter than "no `android.*` imports": with Android as the only target, `commonMain` compiles against Android and the JVM, so any JVM-only library would slip through until another platform is added.
  - **`commonMain` doesn't use platform packages written out in full:** `android.`, `java.`, `javax.`, `okhttp3.` and the like aren't imports, so the import rule can't see them. This found `RedditApi.resolveShareLink` building its own `okhttp3.OkHttpClient`, which now uses a Ktor client from `createHttpClient(followRedirects = false)`. The OkHttp engine follows redirects itself, so the factory turns them off in both Ktor and OkHttp.
  - **UI code doesn't use the API client:** files in a `ui` package, in both modules (so screens and view models), can't mention `RedditApi` or `io.ktor`. `KarmaKameleonApp.kt` called `RedditApi.resolveShareLink`; it now goes through `PostRepository`. `AuthManager`, `OAuthRedirect` and `CommentOrMore` live in the `data.api` package but aren't the client, so the UI may still use them.
  - **`suspend` functions don't use `runCatching`:** the half of CLAUDE.md's errors rule that Detekt doesn't cover (`TooGenericExceptionCaught` already catches `catch (e: Exception)`). Lambdas that suspend, like the block passed to `launch`, can't be told apart from other lambdas, so they aren't checked.

  Every assertion is `strict`, so a rule fails if its scope is empty instead of passing without checking anything, and `RulesTest` checks each pattern against code it should and shouldn't match. The test task declares the checked source files as inputs; without that, Gradle would skip the tests as up to date after a source change, since Konsist reads the sources at runtime. The patterns read the source text, so a match in a comment or string counts too; reword it if that happens. The share link change was smoke-tested on the emulator by pasting a share link into Search, which opened the right post. A JVM integration test for it isn't possible: the app's OkHttp client parses cookies, which needs an Android context.
- [x] **Diff coverage gate with Kover** (replacing the unused JaCoCo setup), e.g. 80% of changed lines covered.
  *Value:* models skip tests unless something forces them. Measuring only changed lines is fair while `androidApp` has no tests.
  *Notes:* Kover 0.9.11 replaces JaCoCo in `shared` (`./gradlew :shared:koverHtmlReport` for a report). Kover has no diff coverage of its own, so the root `diffCoverage` task does it: it reads Kover's XML report and `git diff` from where HEAD branched off `origin/main` (`-Pcoverage.base=<ref>` to compare with something else), and fails when fewer than 80% of the changed lines with code are covered (`-Pcoverage.minimumPercent=N` overrides it), listing the uncovered ones. A line counts as covered if any of its code ran. Uncommitted and untracked files count too, so it can be run before committing. Blank lines, comments and lines Kover has no code for (most declarations) aren't counted, so a change with no measurable lines passes. Only `shared`'s `commonMain` and `androidMain` are measured; add `androidApp` once Phase 4 gives it tests. The PR checks' Unit Tests job runs it after the tests, with the full history checked out so `origin/main` is there. When a `.env` client ID is set, the integration tests in `androidHostTest` call Reddit and cover more of `RedditApi` than in CI, which has no client ID, so a change there can pass locally and fail in CI. Tried on the six PRs before it (`-Pcoverage.base=HEAD~6`), it reported 45 of 68 changed lines covered (66%), with the misses in `CommentViewModel`'s reply code and `AuthManager`. Kover's HTML report brings in FreeMarker 2.3.32, which has a critical advisory (GHSA-27j2-h3m2-8237), so FreeMarker 2.3.35 is in the `security-fixes` bundle and the Kover plugin is declared in the root build, where those constraints apply.
  *Why 80%:* it's high enough that new code comes with tests, and low enough that the misses can be the lines that are hard to test or not worth testing, like platform setup that needs an Android device (the Koin module that opens the token settings needs a `Context`) and logging in error paths. Don't raise it until mutation testing (Phase 4) shows the tests actually assert things: coverage only measures which lines ran, and a higher target mostly pushes a model to write tests that run code without checking it, like the 21 early-returning tests in #34. Even then, 85–90% is about the useful ceiling. Not 100%: some lines can't run in host tests at all, so reaching it means excluding code from the report or suppressing it, which CLAUDE.md asks to avoid, or writing tests whose only job is to execute lines. Requiring every instruction on a line to be covered doesn't work either: Kotlin compiles hidden code onto ordinary lines (null checks, `?.` and `?:` paths, default arguments, `when` fallbacks, coroutine state machines), so lines would fail for paths that can't happen. A line counts as covered even if only one of its paths ran (`error.message ?: errorMessage` with no test for a missing message), so `diffCoverage` also reports how many branches on the changed lines are covered, and lists the lines with branches no test took. It doesn't fail on them yet: #58 is to pick a threshold from the numbers seen on a few PRs, probably starting around 60%, since only 26% of branches are covered today. The existing code was at 61% of lines in CI when #56 set out to raise it. Its five PRs tested the parser, `RedditApi`, the view models, `AuthManager`, `InboxPoller`, the Koin module and the HTTP clients, and removed code nothing used, which left only the Android-only Koin module and default-argument lines uncovered. `:shared:koverVerify` (run in the Unit Tests job) fails if the whole of `shared` drops below 80%.

## Phase 4: deeper checks

- [ ] **Tests for `androidApp`:** Robolectric for UI logic, and screenshot tests (Roborazzi or Paparazzi).
  *Value:* the 49 files in `androidApp` have no tests. Screenshot diffs show exactly what changed visually, without anyone having to look at every UI change in the app (the recent unreadable flair colors are the kind of bug this catches).
- [x] **Dependency Analysis Gradle Plugin.**
  *Value:* finds unused dependencies, `implementation` vs `api` mistakes and transitive dependencies used without being declared. Models add libraries and rarely remove them.
  *Notes:* `buildHealth` is part of `qualityGate`, and every kind of finding fails it. It's applied to the root and to each module, because applying it to the root alone found nothing. Libraries published as a family of artifacts in one Maven group (Compose, Media3, Coil, Koin and so on) are bundles in the root build file, so using `ui-text` through a declared `ui` is fine. Ktor and multiplatform-settings aren't bundled: bundling them hid an unused artifact and gave wrong `api` advice. `kotlin-test-junit` is excluded because `kotlin("test")` picks it by itself. Fixing the first report removed five unused libraries (`kotlinx-datetime`, `ktor-client-auth`, `multiplatform-settings-coroutines`, `media3-ui`, `ui-tooling-preview`), made the types `shared` exposes `api`, and switched to AndroidX's own multiplatform `lifecycle-viewmodel`. 3.19.2 only claims support for AGP up to 9.3.1 and prints a warning on 9.4.1, but its results were correct.
- [x] **APK size check:** fail when the release APK grows more than N% compared with `main`.
  *Value:* catches a large library added by accident, or R8 rules that stop shrinking.
  *Notes:* the `APK Size` job in the PR checks fails when the unsigned release APK grows by more than 5% (about 220 KB at 4.47 MB). It compares with `main`'s APK, built in a parallel job from the first parent of the PR's merge commit, so the check adds about a minute, not a second build's worth. 5% catches a big library or R8 shrinking turned off, not ordinary feature work: removing the unused `media3-ui` in #69 saved 892 KB (17%). Release builds of the same commit are the same size to the byte, so there's no noise to allow for. When growth is intended, add the `apk-size-ok` label and re-run the job, which reads the labels when it runs. It runs even when a build fails, because a skipped required check counts as passing. It's CI-only, since it needs a second release build. Found along the way: the Media3 keep rule stops R8 from shrinking any of Media3 (#70).
- [x] **PR size check:** warn above about 500 changed lines.
  *Value:* smaller PRs make each checker's findings easier to act on and keep an AI reviewer accurate.
  *Notes:* the `PR Size` job counts the added and deleted lines between the PR's merge commit and `main`, and above 500 it adds a warning annotation. It never fails and isn't required. Renames and moves count only their changed lines, and the Detekt and CPD baselines don't count, so a PR that shrinks a baseline isn't flagged. Of the last 30 PRs, about a quarter would have warned, mostly the test PRs (#62 to #65) and the refactor in #28.
- [x] **AI review bot** (Claude Code GitHub Action), advisory only, not a required check.
  *Value:* static tools find patterns; a reviewing model can tell whether the code makes sense and spot logic bugs, poor abstractions and missed reuse. It isn't deterministic, so it doesn't block merges.
  *Notes:* `claude-review.yml` reviews each PR when it opens and after every push, and a new push cancels a review that's still running. It authenticates with the owner's Claude subscription (the `CLAUDE_CODE_OAUTH_TOKEN` secret, from `claude setup-token`) and posts with the job's own token instead of the Claude GitHub App, so it can only read the code and comment on the PR, as github-actions[bot]. Claude can only read files, run `gh pr comment`, `gh pr diff` and `gh pr view`, and read the PR's review comments with `gh api`. Each run reads the earlier review comments and summary, doesn't raise a finding again, and replaces its summary instead of adding another, so pushing again doesn't repeat the review. Fork PRs, Dependabot PRs and drafts are skipped, since forks and Dependabot don't get the secret. The prompt points it at what the static checks can't find, and at CLAUDE.md, which the action always reads from the base branch, so a PR can't change the review's instructions.
